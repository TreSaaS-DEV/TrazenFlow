# Conceptual data model

**Status:** Logical model for review only. No migrations or database objects have been created.

## 1. Tenancy root

A user may belong to multiple workspaces. All business resources belong to exactly one workspace unless a later reviewed requirement states otherwise.

Core identity and tenancy entities:

- **user profile:** identity-provider subject, display metadata, creation and lifecycle timestamps. Password hashes are not stored by the application when using a managed auth provider.
- **workspace:** tenant root, name, settings, status and lifecycle timestamps.
- **workspace membership:** user-to-workspace relationship, role, status, invited-by and accepted-at.
- **workspace role/permission:** initial fixed role set; custom roles can be deferred.

Authorization must verify an active membership for the requested workspace and the required action. Never accept a workspace ID as proof of membership.

## 2. Workflow entities

- **workflow:** stable identity, workspace ID, name, description, ownership, status and timestamps.
- **workflow draft/version:** immutable published version number, graph definition, node config schema version, creator, published-at and content hash.
- **workflow trigger:** event/schedule/manual trigger configuration scoped to a version or stable workflow trigger.
- **workflow secret reference:** pointer to a credential record/version; never the secret value itself.
- **workflow permission policy:** allowed tools, model providers, budgets and approval rules associated with a version or governed policy revision.

Published versions are immutable. Draft changes create a new publication rather than rewriting a version used by previous runs.

## 3. Execution entities

- **workflow execution:** workspace, workflow ID/version, state, initiator, idempotency key, input reference, snapshot reference, started/finished timestamps, cancellation metadata and terminal outcome.
- **execution step:** execution ID, node ID, attempt, state, timing, output reference and sanitized error metadata.
- **execution event:** append-oriented lifecycle events with actor/source, event type, timestamp and correlation ID.
- **job/queue record:** durable scheduling/delivery data such as job type, payload reference, deduplication key, attempt count, next-run time, lease owner, lease expiry, heartbeat and status.
- **approval request:** execution/step reference, requested action, requester, approver policy, decision, decision timestamp and sanitized context reference.
- **worker heartbeat/lease:** either represented in the queue implementation or a separate operational record, depending on selected library.

Execution inputs and outputs can be large or sensitive; prefer bounded JSON metadata plus references to encrypted/object storage rather than unbounded database blobs.

## 4. AI and tool governance

- **provider connection:** workspace-owned provider, provider type, credential reference, enabled state and permitted model policy.
- **model policy:** provider/model allow-list, budget limits, rate limits, data handling rules and approval threshold.
- **AI call record:** execution/step reference, provider, model, usage metadata when provided, latency, outcome and estimated cost.
- **tool/integration permission:** workspace, integration, action scope and policy.
- **budget ledger:** append-oriented usage/cost events and budget reservations to prevent concurrent calls from overspending.
- **audit event:** actor, workspace, action, target reference, timestamp, outcome, request ID and safe metadata.

Do not log raw API keys, OAuth refresh tokens, or sensitive prompt/file contents in these records.

## 5. Files and derived data

- **file object:** workspace, uploader, object key, original filename (sanitized for display), size, checksum, detected media type, scan status, retention state and timestamps.
- **upload session:** workspace, user, intended object key, expected size/checksum, multipart state, expiry and completion status.
- **file processing job:** source object, pipeline/version, state, retry details, limits applied and output references.
- **file derivative:** extracted text, preview, chunks, embeddings or other derived output references; each inherits workspace scope and source lineage.
- **file access grant:** short-lived or scoped authorization record if needed; do not make public buckets the default.
- **retention/deletion event:** record lifecycle state and downstream cleanup result.

Object keys should be generated by the server and tenant-scoped. User-supplied filenames must never define storage paths.

## 6. Integrations and credentials

- **integration installation:** workspace, integration type, owner, enabled/disabled status, scopes and provider account metadata.
- **credential secret:** encrypted ciphertext, key version, nonce/tag metadata, rotation status and secret type; the encryption key must not be stored alongside ciphertext.
- **webhook endpoint:** workspace, secret reference, enabled status, subscribed events, rate limits and last delivery metadata.
- **webhook delivery:** event ID, target, attempt, signature version, result and retry schedule.
- **OAuth state/nonce:** short-lived, one-time state bound to user/workspace/callback; never trust an unverified callback.

## 7. Desktop-specific entities

If desktop registration is needed:

- **desktop installation:** user/workspace association, device identifier, app version, last seen and revoked status.
- **local folder authorization:** explicit user grant, display path/identifier, allowed event types, pause status and revocation timestamp.

Do not store more local filesystem information than required. Avoid treating a desktop installation ID as authentication; use revocable, short-lived credentials.

## 8. Indexes, constraints and tenancy

Required design properties:

- Every tenant-owned row carries a non-null `workspace_id`.
- Foreign keys should include workspace consistency where feasible, or use composite unique keys such as (workspace_id, id) and composite references to prevent cross-tenant linking.
- Index workspace_id with frequently filtered columns.
- Unique idempotency keys are scoped to the relevant workspace/action or execution contract.
- Queue claims must be atomic; leases include expiry and fencing/version tokens to reject stale workers.
- State transitions use constrained enums/checks and transactional transition functions.
- RLS policies use authenticated identity and verified active membership, not client-provided role claims alone.
- Storage authorization must independently verify workspace ownership and file record status.

## 9. Migration strategy

- Version all schema migrations in source control.
- Apply migrations in a disposable development environment first.
- Require backward-compatible expand/migrate/contract steps for high-risk changes.
- Never modify production schema by manually editing tables.
- Maintain migration rollback or forward-fix instructions.
- Run schema and RLS policy tests for both allowed and denied cases.
- Seed only synthetic test users/workspaces and dummy credentials.

The exact table names, column types, indexes, partitioning, retention and RLS SQL belong to a later approved implementation milestone.
